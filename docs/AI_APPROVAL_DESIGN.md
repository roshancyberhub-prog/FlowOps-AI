# Milestone 4: qualification, drafts and protected mock delivery

Status: implemented and accepted in run 40747693463, with 82 backend tests and five browser journeys. The complete interface, edited-review invalidation, current-approver/fact checks and simulated receipt flow are verified. No live provider is connected.

The source CHATGPT.md explicitly authorizes a safe mock when provider credentials are unavailable. The credential check found no OpenAI key. Implement a provider-neutral interface and labelled deterministic mock; do not add live OpenAI calls or create/reuse a key without a separate credential decision. Live AI/provider verification remains unavailable. This is the user's explicit fallback, rather than an implicit credential choice.

1. Add strict Qualification and DraftContent Pydantic outputs. Qualification includes bounded fit category, model-reported confidence, reasoning, missing information and next step. Recipient and permissions are always server-controlled. Reject unexpected fields, invalid output, empty content and CR/LF in subjects. Keep provided lead facts separate from generated inference.
2. Add an async provider protocol returning raw completion content plus provider/model/prompt-version/usage metadata. Validate at the application boundary. AI_PROVIDER=disabled by default; .env.example opts explicitly into mock. The mock reports simulated=true and never contacts a service. Its qualification follows recorded rule score and is labelled as a demonstration; its draft uses supplied facts and the configured value proposition. Support only the known initial_follow_up template.
3. Persist EmailDraft (organization, optional stored lead, execution/node unique, server-bound recipient, subject/body, qualification, provided facts, metadata, revision/status/timestamps). The generate node saves that record/context in the step transaction. New drafts invalidate context approval. Existing baseline/provider failure history must remain accurate.
4. Request approval loads the current stored draft and includes its exact snapshot/revision in the approval payload. Approvals are hash/revision-bound. The decision updates the draft status and resumes through the existing outbox transaction. Generic continue approvals can never authorize email.
5. Draft editing requires a writer and locks execution before draft/approval. Permit edits only while unapproved and the run is active; reject edits once approved/queued for sending. Increment draft revision; replace any pending email approval payload, increment its revision and recompute hash. Update context transactionally. Old approval submissions return 409.
6. Send requires the stored approved email request for this execution, matching payload hash, draft ID/revision/content/recipient and current active stored lead email for live mode. Test mode always forces mock. EMAIL_PROVIDER defaults disabled; example configuration explicitly selects mock. The mock creates a deterministic provider message ID from the execution/node idempotency key and makes no external send.
7. Persist EmailDelivery unique per execution/node, linked to approval/draft, with provider, recipient, idempotency key, payload hash and simulated status. Mock steps must say external_message_sent=false and draft status simulated. Keep the existing uncertain-external-intent recovery conservative. No force resend endpoint.
8. Add scoped draft/delivery read APIs and writer draft-edit API. A lead draft-generation endpoint may queue a user-selected published workflow containing a draft node (rather than generating inside an HTTP request). Read results on lead details and execution history. Display mock provider and execution mode in approval screens.
